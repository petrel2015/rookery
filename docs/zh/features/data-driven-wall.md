# 数据驱动的项目墙

[English](../../en/features/data-driven-wall.md) | 简体中文 · 功能[索引](./index.md) · 主 [README](../../../README.zh.md)

## 概述

整堵墙——每张卡片、每个分类、每个数量角标、每条链接——都由一个纯
JavaScript 文件（`src/data/projects.js`）渲染而来；任何组件都不硬编码
项目信息。

## 背景

个人 side project 会不断散落到各个仓库。常规解法是在个人主页 README
里维护一份「我的项目」清单——纯链接、无截图，而且会腐烂：加一条要
改散文、改了也说不出东西长什么样。成熟的作品集 CMS 能解决，但拖进来
账号、数据库和运行时服务——静态展示墙根本不需要这些。

## 问题

具体到手维护页面时：

1. 加一个项目要在多处改标记（卡片、数量、分类区块）——每次编辑都是
   一次弄坏布局的机会。
2. 没有好截图的项目会阻塞发布，因为空图片框看起来就是坏了。
3. 内容与展现纠缠，别人 fork 后得先逆向工程组件才能列出自己的作品。

## 目标

- 加（删）一个项目 = 在一个文件里追加（删除）一条记录 + 一张图片
  文件——不动组件。
- 对**没有封面图**、**没有在线演示**的记录，墙都能正确渲染；两者都
  不是错误状态。
- 封面图随墙自带，渲染不依赖被链接仓库的可用性。
- 同一个构建可托管在任意路径（相对 base）——fork 与自托管必须零配置。
- 零后端、零运行时数据拉取、除 Vite 本身外零构建期内容管线。

## 非目标

- **不做 CMS、不做管理后台。** 数据文件就是接口；在文本编辑器里改它
  就是预期工作流。
- **不做运行时 GitHub API 集成。** 仓库元数据（star、描述、topic）刻意
  不拉取——墙必须「离线于 GitHub」也能工作，且不受限额与令牌拖累。
- **不做 i18n 层。** UI 文案是中文；翻译不在本设计范围。
- **不做动态分类或标签系统。** 恰好三个分类（`ext` / `tool` / `game`）
  覆盖作者的实际产出；自由标签系统在这个规模下只会增加 UI、不增加
  浏览收益。
- **不做搜索与排序。** 12 项规模下，筛选片足够。
- **不做定时重建**（如每日 CI 刷新封面）。墙随作者改动而变化。

## 方案概览

`src/data/projects.js` 导出两个纯常量——`CATEGORIES`（id + 标签文案）
与 `PROJECTS`（记录数组；字段说明见
[使用指南](../usage.md#项目记录字段)）。`App.vue` 持有两份 UI 状态
（当前分类、布局），用一个 `computed` 过滤出可见卡片；
`ProjectCard.vue` 以两种布局之一渲染一条记录。代码库里没有任何其它
位置提及具体项目。

封面住在 `public/covers/`，以相对路径（`covers/x.webp`）引用，Vite 会
把它复制进构建，且在任意子路径下都能解析——与 `base: './'` 一起，
这就是构建「主机无关」的原因。

占位封面是纯 CSS（22 px 间距的 repeating linear-gradient 坐标纸）加
记录的 `name`——有汉字取首字，否则取前两个拉丁字母并大写。

用户偏好（主题、布局）经 `localStorage` 持久化；主题由 `index.html`
里的内联脚本在首屏绘制前恢复，避免暗色用户看到一次闪白。

## 详细行为

- **默认值。** 新访客：分类 `all`、布局 `grid`、主题取
  `prefers-color-scheme`。
- **链接解析。** 卡片标题与封面指向 `demo || github`；GitHub 按钮始终
  指向 `github`。均新标签页打开并带 `rel="noopener"`。
- **数量。** 分类片数量由数组计算（`all` = 长度，其余 = 过滤长度）——
  数字不可能与数据不一致。
- **空状态。** `cover` 空 → 占位封面；`demo` 空 → 只有 GitHub 按钮；
  某分类零记录 → 显示「该分类暂无项目。」。
- **截断。** `desc` 经 `-webkit-line-clamp` 截 3 行（网格）/ 2 行
  （列表），记录长度永远不会破坏卡片等高。
- **`coverFit`。** `'cover'`（默认）铺满 16:10 盒；`'contain'` 居中留
  14% 边距，适配图标类素材。
- **错误。** 畸形记录（如缺 `github`）不会被优雅捕获——因为 Vue 按
  组件渲染，其它卡片仍会出现，但控制台会有报错。数据质量靠评审保证，
  不靠运行时校验。
- **图片。** 封面 `loading="lazy"`；断言脚本会验证每张已登记封面真实
  加载（`naturalWidth > 0`）。

## 用户体验

- 分类片与视图切换位于吸附工具条（桌面端），滚动项目墙时始终可达。
- 切分类或视图时有 160 ms 淡入过渡（`mode="out-in"`），避免生硬重排。
- 卡片悬停上浮 3 px 并带轻投影；标题箭头向强调色过渡；封面放大
  1.025×——轻、安静的反馈。

  ![项目墙总览](../../img/overview-grid-light.webp)

- 占位封面被设计成「有意为之的编辑风格」（坐标纸 + 首字 + 红点），
  而不是故障态。

  ![占位封面](../../img/cover-fallback.webp)

## 兼容性与历史影响

无历史行为受影响。本设计即项目首次发布（v0.1.0，2026-08-27）的初始
架构；没有更早的数据格式需要迁移。

## 数据与隐私影响

本设计恰好引入两个 `localStorage` 键（`pw-theme`、`pw-layout`），不引入
任何网络行为。数据文件本身只包含公开信息（名称、描述、公开 URL）。
完整审计见[隐私说明](../privacy.md)。

## 性能影响

数据模块打进单一 JS chunk（v0.1.0 整个应用：80.5 kB 原始 / 33.77 kB
gzip，含 Vue；CSS 8.55 kB / 2.32 kB gzip）。渲染是对不超过几十个元素的
一个 `computed` 过滤——该规模下无需虚拟化，也没计划做（见非目标）。
页面重量的大头是封面图；它们懒加载，推荐 WebP 格式。

## 当前局限

（尚未做到的事——区别于上面「主动不做」的非目标。）

- 分类文案只有中文，因为没有 i18n 层。
- 记录没有运行时校验；写错了会在浏览器控制台里显性报错，而不是在
  构建步骤里。
- 封面图需从源仓库手动复制；没有自动化。
- 断言脚本（`scripts/verify.mjs`）硬编码了当前数据规模（12 卡 / 11
  封面），数据增长时需同步更新。
